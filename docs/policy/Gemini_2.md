# 개인 설정 (Personal Preferences)

# [StudyGame] 세션 시스템 규칙

## 1. 메타 동작 (포니테일 모드 / Ponytail Mode)

현재 프로젝트(StudyGame)에서는 폴더 경로와 무관하게 매 턴마다 항상 다음 원칙을 준수해야 합니다.

- 코드를 제안하거나 수정할 때는 항상 먼저 `/ponytail-audit`, `/ponytail-debt`, `/ponytail-gain`, `/ponytail-review` 관점에서 분석하세요.
- 오버엔지니어링(YAGNI)을 엄격히 방지하고, 최소한의 복잡도로 현재 필요한 기능만을 구현하세요.
- **가장 중요:** 코드를 작성하거나 수정하기 전에는 반드시 저(사용자)에게 실행 허가를 구하고 승인을 기다리세요.
- **엄격한 UI 규칙:** 아무리 편리해 보이더라도 명시적인 허가 없이 버튼이나 UI 요소를 절대 추가하지 마세요. 강제로 씬(Scene)을 전환하거나 사용자 설정을 우회하지 마세요.

## 2. 게임 폴리싱 및 연출 방향 (Game Polish & Direction)

'상용 모바일/PC 게임의 완성도 기준'에 비추어 현재 게임을 검토하세요. 새로운 콘텐츠를 추가하기보다, 먼저 '기존 게임플레이가 충분히 전달되지 않거나 전반적인 퀄리티를 떨어뜨리는 요소'를 찾으세요.

- 단순히 화려하게만 만들지 말고, **의도가 명확하고 일관되며 플레이어가 자신의 행동에 따른 원인과 결과를 즉각 이해할 수 있는 상태**를 목표로 하세요.
- 현재 프로젝트에서 중복된 이펙트, 중복 코드, 미사용 기능, 역할이 겹치는 UI, 일관되지 않은 스타일을 식별하고, 이에 대해 **유지 / 병합 / 삭제** 여부를 제안하세요.

## 3. 분석 파이프라인 (Analysis Pipeline)

중요한 이벤트와 인터랙션(특히 로직은 존재하나 연출이 부족한 이벤트)을 파악할 때는 다음 흐름에 따라 분석하세요.

- [입력 → 예비 동작(Anticipation) → 실행(Action) → 충돌/변화 → 결과 → 회복/정리]

**체크리스트 (체감 임팩트가 큰 항목만 제안하고, 과도한 연출은 배제):**

- 시각 / 청각 / 햅틱 피드백 (모바일 플랫폼 고려)
- 트윈(Tween) / 선형 보간(Lerp) / 이징(Easing)을 활용한 움직임 및 수치 변화
- 예비 동작(Anticipation) / 스쿼시 & 스트레치(Squash & Stretch) / 팔로스루(Follow-through) / 2차 동작(Secondary Motion)
- 전투 피드백 (히트 스톱, 피격 플래시, 넉백, 화면 흔들림 등)
- 시각 효과(파티클, 트레일, 임팩트 등) 및 사운드 동기화
- 상태 변화 표현 (대미지 미리보기, 잔상 체력 바, 카운트업 등)
- 카메라 연출 (줌, 킥, 이동, 트래킹)
- UI/UX (정보 위계, 가독성, 등장/퇴장 타이밍, 버튼 상태 변화 등)
- 중요 시퀀스의 '연속적인 경험' (예: 보스 처치 후 남는 여운과 보상으로 이어지는 흐름)

각 이벤트의 게임플레이 내 중요도에 비례하여 연출 강도를 결정하세요. (모든 이벤트에 동일한 수준의 연출을 적용하지 마세요).

## 4. 출력 형식 (Output Format)

분석 및 제안 시 아래 형식을 엄격히 준수하세요.

1. **[게임 폴리싱 제안]** (다음 순서대로 정렬)

- 우선순위 1: 즉시 수정 시 체감 효과가 큰 항목
- 우선순위 2: 적은 비용으로 개선 가능한 항목
- 우선순위 3: 추후 다듬을 디테일 항목

- (각 항목마다 '현재 구현 상태 / 문제점 / 개선 효과 / 구현 난이도' 명시)

2. **[포니테일 코드 분석]** (위 제안을 구현하기 위한 코드 관점 분석)

- `/ponytail-audit`: 제안된 연출을 구현할 때 예상되는 병목 현상이나 기존 아키텍처와의 충돌 분석.
- `/ponytail-debt`: 이 연출을 추가함으로써 발생할 수 있는 기술적 부채 (예: 과도한 코루틴 사용, 하드코딩).
- `/ponytail-gain`: 이 구조를 통해 얻을 수 있는 유지보수 측면의 이점.
- `/ponytail-review`: 해당 연출 로직이 과도하게 일반화되지 않았는지 YAGNI 원칙에 입각한 검증.

3. **[실행 허가 요청]**

- 위 제안을 바탕으로 실제 코드를 작성하기 전에 반드시 사용자의 동의를 구해야 합니다. (예: "우선순위 1 항목에 대한 코드 수정을 먼저 진행할까요?")
